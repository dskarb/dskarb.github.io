Problem: brute force nie skaluje się

W module 08 porównywaliśmy zapytanie z każdym dokumentem. Dla 1 mln dokumentów po 1536 wymiarów to 1,5 mld mnożeń na każde zapytanie. Algorytmy ANN (Approximate Nearest Neighbor) sprawdzają tylko ułamek wektorów i znajdują prawie zawsze właściwych sąsiadów. Miarą jakości jest recall@k: jaki odsetek prawdziwych k najbliższych sąsiadów znalazł indeks.

HNSW — graf „małego świata”

Najpopularniejszy algorytm. Wektory są węzłami grafu połączonymi z bliskimi sąsiadami. Wyszukiwanie zaczyna w punkcie wejścia i zachłannie skacze do sąsiada bliższego zapytaniu, aż nie da się zbliżyć bardziej. Kliknij w płótno, żeby zadać zapytanie:

Krajobraz baz wektorowych

Postgres + pgvector

Wektory obok danych relacyjnych, transakcje, JOIN-y, filtry SQL. Dostępne w Supabase, Neon, RDS. Domyślny wybór na start.

Qdrant / Weaviate / Milvus

Dedykowane, open-source, self-hosted lub chmura. Bogate filtrowanie, hybrid search, skala setek milionów.

Pinecone

W pełni zarządzane (serverless). Zero ops, płacisz za użycie.

Chroma / LanceDB

Proste, embedded (jak SQLite dla wektorów). Świetne do prototypów i aplikacji lokalnych.

FAISS

Biblioteka Meta (nie baza): najszybsze indeksy w pamięci, bez metadanych i trwałości.

Elasticsearch / OpenSearch / MongoDB Atlas / Redis

Wyszukiwanie wektorowe dodane do istniejących systemów — dobre, gdy już ich używasz.

pgvector — od zera do zapytania

create extension if not exists vector; create table documents ( id bigserial primary key, tenant_id uuid not null, -- izolacja klientów! source text not null, -- np. ścieżka pliku / URL chunk_index int not null, content text not null, metadata jsonb default '{}', embedding vector(1536) not null, -- wymiar = wymiar modelu embed_model text not null default 'text-embedding-3-small', -- kolumna do wyszukiwania pełnotekstowego (dla hybrid search) fts tsvector generated always as (to_tsvector('simple', content)) stored ); -- indeks ANN: HNSW z metryką cosine create index on documents using hnsw (embedding vector_cosine_ops) with (m = 16, ef_construction = 64); create index on documents using gin (fts); create index on documents (tenant_id); -- Operatory pgvector: <=> cosine distance <-> L2 <#> ujemny iloczyn skalarny import pg from "pg"; const pool = new pg.Pool({ connectionString: process.env.DATABASE_URL }); const toVec = (v: number[]) => JSON.stringify(v); // pgvector akceptuje '[0.1,0.2,...]' export async function upsertChunks(tenantId: string, source: string, chunks: string[], vectors: number[][]) { const client = await pool.connect(); try { await client.query("begin"); // re-indeksacja pliku: usuń stare chunki, wstaw nowe (atomowo) await client.query("delete from documents where tenant_id = $1 and source = $2", [tenantId, source]); for (let i = 0; i < chunks.length; i++) { await client.query( `insert into documents (tenant_id, source, chunk_index, content, embedding) values ($1, $2, $3, $4, $5)`, [tenantId, source, i, chunks[i], toVec(vectors[i])], ); } await client.query("commit"); } catch (e) { await client.query("rollback"); throw e; } finally { client.release(); } } export async function searchVector(tenantId: string, queryVec: number[], k = 5) { const { rows } = await pool.query( `select id, source, content, 1 - (embedding <=> $2) as similarity from documents where tenant_id = $1 -- filtr metadanych order by embedding <=> $2 -- ten zapis używa indeksu HNSW limit $3`, [tenantId, toVec(queryVec), k], ); return rows; }
Filtrowanie a indeks ANNGdy filtr jest bardzo selektywny (np. tenant ma 0,1% wszystkich wektorów), indeks HNSW może zwrócić za mało wyników — przeszukuje graf, a potem odrzuca niepasujące (post-filtering). Rozwiązania: większy hnsw.ef_search, tryb iteracyjnego skanowania w nowszych wersjach pgvector, partycjonowanie per tenant lub bazy z natywnym filtrowaniem w trakcie przeszukiwania grafu (Qdrant, Weaviate).

Wyszukiwanie hybrydowe

Embeddingi świetnie łapią znaczenie, ale gorzej radzą sobie z dokładnymi ciągami: kody produktów („XR-4410”), nazwiska, numery przepisów, skróty. Klasyczne wyszukiwanie leksykalne (BM25, full-text) robi to doskonale. Wyszukiwanie hybrydowe łączy oba rankingi.

Reciprocal Rank Fusion (RRF) łączy rankingi bez potrzeby normalizowania wyników z różnych skal: score(d) = Σ 1 / (k + pozycja_d), typowo k = 60. Dokument wysoko w obu listach wygrywa.

Kalkulator RRF

BM25: D3, D1, D7, D2, D9 · Wektory: D1, D5, D3, D8, D2

-- $1 = wektor zapytania, $2 = tekst zapytania, $3 = tenant_id with semantic as ( select id, row_number() over (order by embedding <=> $1) as rank from documents where tenant_id = $3 order by embedding <=> $1 limit 20 ), keyword as ( select id, row_number() over (order by ts_rank_cd(fts, websearch_to_tsquery('simple', $2)) desc) as rank from documents where tenant_id = $3 and fts @@ websearch_to_tsquery('simple', $2) order by ts_rank_cd(fts, websearch_to_tsquery('simple', $2)) desc limit 20 ) select d.id, d.source, d.content, coalesce(1.0 / (60 + s.rank), 0) + coalesce(1.0 / (60 + k.rank), 0) as rrf_score from semantic s full outer join keyword k on s.id = k.id join documents d on d.id = coalesce(s.id, k.id) order by rrf_score desc limit 5;
Polski full-textPostgres nie ma wbudowanego słownika języka polskiego, więc konfiguracja 'simple' nie sprowadza słów do formy podstawowej („faktury” ≠ „faktura”). Pomaga rozszerzenie ze słownikiem polskim (Hunspell/ispell), lematyzacja przed indeksowaniem albo dedykowane wyszukiwarki (Elasticsearch z analizatorem polskim). Część wektorowa nie ma tego problemu.

Jak wybrać

< 1 mln wektorów i masz Postgresa?→pgvector
Prototyp / aplikacja lokalna?→Chroma, LanceDB
Setki mln wektorów, złożone filtry, hybrid?→Qdrant, Weaviate, Milvus
Zero ops, budżet na usługę?→Pinecone lub zarządzane wersje powyższych
Użytkownicy wpisują kody części („ZX-2210-B”) i wyszukiwarka wektorowa zwraca podobne, ale złe części. Co poprawi wyniki?
Kody i identyfikatory to dokładne dopasowania leksykalne — mocna strona BM25, słaba strona embeddingów. Hybryda bierze to, co najlepsze z obu.
