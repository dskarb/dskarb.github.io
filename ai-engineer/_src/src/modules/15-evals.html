Ewaluacja, observability i LLMOps

To, co odróżnia demo od produktu. Jak mierzyć jakość systemu AI, wyłapywać regresje, śledzić koszty i niezawodnie działać na produkcji.

TL;DR Evale to testy jednostkowe AI. Bez nich każda zmiana promptu, modelu czy chunkingu to zgadywanie. Zbuduj zestaw przypadków z realnych danych, oceniaj automatycznie (kod + LLM-as-judge), uruchamiaj przy każdej zmianie, a na produkcji loguj każde wywołanie z kosztem i czasem.

Dlaczego zwykłe testy nie wystarczą

Klasyczny kod

add(2, 2) === 4 — jedno poprawne wyjście, deterministyczne, test przechodzi albo nie.

System LLM

„Streść ten e-mail” — tysiące poprawnych odpowiedzi, wynik zmienia się między wywołaniami, a poprawa jednego przypadku może zepsuć dziesięć innych. Potrzebujesz statystyki na zestawie przypadków, a nie pojedynczego asserta.

Zbiór ewaluacyjny

  • Źródła: realne zapytania z logów (najcenniejsze), przypadki zgłoszone przez użytkowników jako błędy, przypadki brzegowe wymyślone przez zespół, ataki (moduł 06), syntetyczne warianty wygenerowane przez model.
  • Rozmiar: 20–50 przypadków na start już daje sygnał. 100–500 dla dojrzałego systemu. Każdy wykryty błąd na produkcji → nowy przypadek.
  • Kategorie: oznacz każdy przypadek (np. „zwroty”, „poza zakresem”, „injection”), żeby widzieć, gdzie system jest słaby.
  • Oczekiwania: wzorcowa odpowiedź, lista faktów, które muszą wystąpić, albo kryteria oceny.

Porównanie wersji promptu

LLM-as-judge — pułapki

Bias pozycji

W porównaniach A/B sędzia preferuje odpowiedź na określonej pozycji. Oceniaj w obu kolejnościach.

Bias długości

Dłuższe odpowiedzi wydają się „lepsze”. Rubryka powinna jawnie nagradzać zwięzłość, jeśli jej chcesz.

Mętne kryteria

„Oceń jakość 1–10” daje szum. Binarne, konkretne kryteria („czy podaje termin?”) są stabilniejsze.

Kalibracja

Porównaj werdykty sędziego z oceną człowieka na 50–100 przypadkach. Przy niskiej zgodności popraw rubrykę.

Evale w CI/CD

name: LLM evals on: pull_request: paths: ["prompts/**", "src/ai/**", "evals/**"] jobs: evals: runs-on: ubuntu-latest steps: - uses: actions/checkout@v4 - uses: actions/setup-node@v4 with: { node-version: 22 } - run: npm ci - run: npx tsx evals/run.ts v3 # exit 1 przy wyniku < 90% blokuje merge env: ANTHROPIC_API_KEY: ${{ secrets.ANTHROPIC_API_KEY }}

To jest testowanie regresyjne dla AI: każda zmiana promptu, modelu, parametrów czy pipeline'u RAG przechodzi przez ten sam zestaw. Dla szybkości możesz mieć mały zestaw „smoke” na każdy PR i pełny zestaw nocny.

Observability na produkcji

Observability w aplikacjach LLM oznacza możliwość odtworzenia, co dokładnie zobaczył model i co zrobił przy każdym żądaniu. Podstawą jest tracing: drzewo zagnieżdżonych operacji (spanów) dla jednego żądania użytkownika.

Narzędzia

Langfuse (open-source), LangSmith, Braintrust, Helicone, Arize Phoenix, Weights & Biases Weave. Standard OpenTelemetry ma konwencje semantyczne dla GenAI.

Metryki techniczne

Latencja p50/p95, TTFT, tokeny i koszt per żądanie/funkcja/użytkownik, % błędów i ponowień, % ucięć na max_tokens.

Metryki jakości

👍/👎 użytkowników, wskaźnik eskalacji do człowieka, odsetek „nie wiem”, online evale (sędzia LLM na próbce ruchu).

// Minimalny wrapper — zanim wdrożysz pełne narzędzie do tracingu export async function traced( name: string, meta: Record, fn: () => Promise, ): Promise { const t0 = performance.now(); try { const res = await fn(); const ms = Math.round(performance.now() - t0); const u = res.usage; const cost = u ? (u.input_tokens * PRICE.in + u.output_tokens * PRICE.out) / 1e6 : 0; logger.info({ span: name, ms, ...meta, tokens: u, costUsd: cost.toFixed(6) }); return res; } catch (err) { logger.error({ span: name, ms: Math.round(performance.now() - t0), ...meta, err: String(err) }); throw err; } } declare const PRICE: { in: number; out: number }; declare const logger: { info(o: object): void; error(o: object): void };

Wzorce produkcyjne — checklista

  • Streaming odpowiedzi w UI i anulowanie przy zamknięciu karty.
  • Timeouty, retry z backoffem, fallback na inny model/dostawcę.
  • Rate limit i budżet per użytkownik (żądania/min, tokeny/dzień) — ochrona przed nadużyciem i rachunkiem-niespodzianką.
  • Cache: prompt caching u dostawcy; cache dokładnych odpowiedzi dla powtarzalnych zapytań; ostrożnie z cache semantycznym (podobne ≠ identyczne pytanie).
  • Kolejki dla długich zadań (agenci, przetwarzanie dokumentów): job w tle + status/webhook zamiast trzymania żądania HTTP.
  • Wersjonowanie promptów w repo, wersja w każdym logu, możliwość szybkiego rollbacku.
  • A/B testy i feature flagi dla nowych promptów/modeli na części ruchu.
  • Przypięte wersje modeli (ID z datą/wersją, nie alias „latest”) + plan migracji przed wycofaniem modelu.
  • Guardrails wejścia i wyjścia, walidacja structured output.
  • Alerty: skok kosztu, wzrost błędów, spadek 👍, wzrost latencji p95.
  • Prywatność logów: maskowanie PII, retencja, kontrola dostępu.
Zmieniłeś model na nowszy „bo jest lepszy w benchmarkach”. Co powinno się wydarzyć przed wdrożeniem?
Nowy model może lepiej wypadać ogólnie, a gorzej w Twoich przypadkach (inny styl, inne zachowanie z narzędziami, inny format). Evale per kategoria + stopniowy rollout to standard.

🧪 Ćwiczenia praktyczne

Skalibruj sędziego LLM na ocenach człowieka, a potem zbuduj raport evali z bramką jakości do CI i policz zgodność sędziego z człowiekiem.
