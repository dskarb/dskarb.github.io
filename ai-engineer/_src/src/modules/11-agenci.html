Agenci AI i tool calling

Jak model „wykonuje akcje”, jak napisać pętlę agenta od zera, jak projektować narzędzia i kiedy agent jest przesadą.

mechanika tool callingReActagent od zera w TSprojektowanie narzędziwzorce workflowmulti-agent
TL;DR Agent = LLM + narzędzia + pętla. Model nie wykonuje niczego sam — zwraca prośbę „wywołaj narzędzie X z argumentami Y”, Twój kod je wykonuje i odsyła wynik. Pętla trwa, dopóki model nie uzna zadania za skończone. Najwięcej jakości daje dobre zaprojektowanie narzędzi, a nie framework.

Spektrum autonomii

Mechanika tool calling

ReAct: myśl → działaj → obserwuj

ReAct (Reasoning + Acting) to wzorzec, w którym model przeplata rozumowanie z akcjami. Zobacz przebieg dla pytania o zamówienie:

Ślad agenta (trajektoria)
userZamówiłem kubki w poniedziałek (nr 481). Czy dotrą przed sobotą? Jeśli nie, chcę anulować.
myślMuszę sprawdzić status zamówienia 481 i przewidywaną datę dostawy.
akcjaget_order({ order_id: "481" })
obserwacja{ status: "oczekuje na towar", eta: "2026-10-20", cancellable: true }
myślDostawa 20.10 to wtorek — po sobocie. Klient chce wtedy anulować. Anulowanie jest możliwe, ale to akcja nieodwracalna — potrzebuję potwierdzenia.
akcjacancel_order({ order_id: "481" }) → system wymaga zgody użytkownika
obserwacjaUżytkownik zatwierdził. { cancelled: true, refund: "3-5 dni roboczych" }
odpowiedźZamówienie dotarłoby dopiero we wtorek 20.10, więc je anulowałem. Zwrot pieniędzy pojawi się na koncie w ciągu 3–5 dni roboczych.

Agent od zera — kompletny kod

Bez frameworka, ~100 linii. Przepisz i uruchom — po tym ćwiczeniu każdy framework agentowy stanie się czytelny.

import Anthropic from "@anthropic-ai/sdk"; const client = new Anthropic(); const MODEL = "claude-sonnet-5-5"; const MAX_STEPS = 10; // bezpiecznik przeciw nieskończonym pętlom // ---------- 1. Definicje narzędzi (to widzi model) ---------- const tools: Anthropic.Tool[] = [ { name: "get_order", description: "Zwraca status, datę dostawy (eta) i czy można anulować zamówienie klienta. Użyj, gdy klient pyta o konkretne zamówienie.", input_schema: { type: "object", properties: { order_id: { type: "string", description: "Numer zamówienia, np. '481'" } }, required: ["order_id"], }, }, { name: "search_faq", description: "Przeszukuje bazę wiedzy sklepu (zwroty, reklamacje, wysyłka, płatności). Zwraca do 3 fragmentów.", input_schema: { type: "object", properties: { query: { type: "string" } }, required: ["query"], }, }, { name: "calculate", description: "Liczy wyrażenie arytmetyczne, np. '129.99 * 3 - 20'. Używaj zamiast liczenia w pamięci.", input_schema: { type: "object", properties: { expression: { type: "string" } }, required: ["expression"], }, }, ]; // ---------- 2. Implementacje (to wykonuje Twój kod) ---------- type Ctx = { userId: string }; const impl: Record Promise> = { async get_order({ order_id }, ctx) { const order = await db.orders.find(order_id); if (!order || order.userId !== ctx.userId) { // autoryzacja z sesji, nie od modelu! throw new Error(`Nie znaleziono zamówienia ${order_id} dla tego klienta.`); } return { status: order.status, eta: order.eta, cancellable: order.cancellable }; }, async search_faq({ query }) { return (await faqSearch(query, 3)).map(r => r.content); // zwięzły wynik, nie cały dokument }, async calculate({ expression }) { if (!/^[\d\s+\-*/().]+$/.test(expression)) throw new Error("Dozwolone tylko liczby i + - * / ( )"); return Function(`"use strict"; return (${expression})`)(); // bezpieczne dzięki whiteliście znaków }, }; // ---------- 3. Pętla agenta ---------- export async function runAgent(userMessage: string, ctx: Ctx) { const messages: Anthropic.MessageParam[] = [{ role: "user", content: userMessage }]; for (let step = 0; step < MAX_STEPS; step++) { const res = await client.messages.create({ model: MODEL, max_tokens: 2000, system: "Jesteś asystentem obsługi klienta sklepu. Korzystaj z narzędzi, zamiast zgadywać. Odpowiadaj krótko po polsku.", tools, messages, }); // odpowiedź asystenta (z blokami tool_use) MUSI trafić do historii messages.push({ role: "assistant", content: res.content }); if (res.stop_reason !== "tool_use") { return res.content.filter(b => b.type === "text").map(b => b.text).join(""); } // model może poprosić o kilka narzędzi naraz — wykonaj równolegle const calls = res.content.filter((b): b is Anthropic.ToolUseBlock => b.type === "tool_use"); const results = await Promise.all(calls.map(async (call): Promise => { try { const fn = impl[call.name]; if (!fn) throw new Error(`Nieznane narzędzie: ${call.name}`); const out = await fn(call.input, ctx); log("tool", call.name, call.input, out); return { type: "tool_result", tool_use_id: call.id, content: JSON.stringify(out) }; } catch (err) { // błąd wraca do modelu — często sam się poprawi (inny argument, inne narzędzie) return { type: "tool_result", tool_use_id: call.id, content: String(err), is_error: true }; } })); // wszystkie wyniki w JEDNEJ wiadomości user messages.push({ role: "user", content: results }); } return "Przepraszam, nie udało mi się dokończyć zadania. Przekazuję sprawę konsultantowi."; } declare const db: { orders: { find(id: string): Promise } }; declare function faqSearch(q: string, k: number): Promise<{ content: string }[]>; declare function log(...a: unknown[]): void;
Na co zwrócić uwagę w kodzie
  • Odpowiedź asystenta z blokami tool_use zawsze wraca do historii, a każdy tool_use_id musi dostać swój tool_result.
  • Błędy narzędzi nie zabijają pętli — trafiają do modelu jako is_error z czytelnym komunikatem.
  • MAX_STEPS + limit tokenów/kosztu per zadanie = ochrona przed „nieskończonym” agentem.
  • Tożsamość użytkownika pochodzi z ctx (sesja), nie z argumentów modelu.

Odpowiednik w OpenAI wygląda bardzo podobnie: narzędzia definiujesz w polu tools (typ function z JSON Schema), model zwraca elementy function_call, a Ty odsyłasz function_call_output z tym samym call_id. Starsze Assistants API zostało wygaszone na rzecz Responses API.

Projektowanie narzędzi — najważniejsza umiejętność

Narzędzia to interfejs dla modelu. Pisz je tak, jak pisałbyś API dla nowego członka zespołu, który nie może zadać pytania.

name: "query" description: "runs query" input: { q: string, t: number, f?: any } → zwraca 5000 wierszy surowego JSON-a → przy błędzie: "Error 500"
name: "search_customer_orders" description: "Wyszukuje zamówienia zalogowanego klienta. Użyj, gdy klient pyta o zamówienie bez numeru. Zwraca max 10 najnowszych." input: { status?: "nowe"|"wysłane"|"dostarczone", since?: "YYYY-MM-DD" } → zwraca: id, data, kwota, status → przy błędzie: "Nieprawidłowa data 'wczoraj'. Użyj formatu YYYY-MM-DD."
  • Nazwa i opis mówią co, kiedy używać i czego nie robi. Opis to prompt.
  • Mało, a dobrze: 5 przemyślanych narzędzi bije 40 cienkich wrapperów na endpointy REST. Łącz typowe sekwencje w jedno narzędzie.
  • Proste argumenty: enumy zamiast dowolnych stringów, jasne formaty, sensowne wartości domyślne.
  • Zwięzłe wyniki: tylko pola potrzebne modelowi, paginacja, przycinanie długich tekstów (każdy token wyniku zajmuje kontekst).
  • Pomocne błędy: komunikat mówi, co poprawić.
  • Bezpieczeństwo: autoryzacja w kodzie, zatwierdzanie akcji nieodwracalnych, idempotencja (ponowienie nie płaci dwa razy).

Wzorce workflow (zanim sięgniesz po agenta)

⛓️ Prompt chaining

Stała sekwencja kroków, z bramkami walidacji między nimi. Np. konspekt → sprawdzenie → artykuł.

🔀 Routing

Klasyfikacja wejścia i skierowanie do wyspecjalizowanego promptu/modelu. Np. reklamacje vs pytania techniczne.

⚡ Parallelization

Niezależne podzadania równolegle (sekcje dokumentu) albo głosowanie (3 oceny, większość wygrywa).

🎼 Orchestrator–workers

Model planuje podzadania dynamicznie i rozdziela je do „pracowników”, potem scala wyniki.

🔁 Evaluator–optimizer

Jeden model generuje, drugi ocenia według kryteriów i odsyła uwagi — pętla do skutku lub limitu.

🤖 Agent

Pętla z narzędziami, model sam decyduje o krokach. Najbardziej elastyczny, najtrudniejszy do testowania.

// Parallelization: niezależne analizy jednocześnie, potem synteza const [security, perf, style] = await Promise.all([ review(diff, "Oceń wyłącznie bezpieczeństwo (injection, auth, sekrety)."), review(diff, "Oceń wyłącznie wydajność (N+1, pętle, pamięć)."), review(diff, "Oceń wyłącznie czytelność i nazewnictwo."), ]); const summary = await review( JSON.stringify({ security, perf, style }), "Połącz trzy recenzje w jedną listę uwag, posortowaną od najważniejszej.", ); declare function review(input: string, focus: string): Promise; declare const diff: string;

Przy długich zadaniach stosuj kompaktowanie: gdy kontekst zbliża się do limitu, streść dotychczasowy przebieg (decyzje, stan, otwarte kwestie) i zacznij z czystą historią + streszczeniem.

Multi-agent

Orkiestrator rozbija zadanie i deleguje do podagentów z własnymi, czystymi kontekstami (np. każdy bada inny temat), a potem scala wyniki. Zalety: równoległość i izolacja kontekstu. Wady: wielokrotnie więcej tokenów, trudniejsze debugowanie, problemy z koordynacją. Sprawdza się w zadaniach szerokich i dających się podzielić (research), gorzej w zadaniach wymagających ciągłego współdzielenia stanu (wspólny kod).

Testowanie agentów

  • Wynik końcowy: czy zadanie zostało wykonane (stan w bazie, poprawna odpowiedź)?
  • Trajektoria: czy użył właściwych narzędzi, w rozsądnej liczbie kroków, bez zbędnych akcji?
  • Odporność: błędy narzędzi, puste wyniki, sprzeczne dane, próby injection w wynikach narzędzi.
  • Koszt i czas: średnia i 95. percentyl tokenów oraz kroków na zadanie.
Agent w 15% przypadków wywołuje narzędzie search z argumentem w złym formacie i się zapętla. Co poprawi sytuację najbardziej?
Model korzysta z opisu narzędzia i komunikatów błędów jak z dokumentacji. Lepszy interfejs = mniej błędów, a pomocny błąd pozwala mu się samodzielnie poprawić.

🧪 Ćwiczenia praktyczne

Porozmawiaj z prawdziwym agentem, który ma narzędzia zapisu i trafia na ukrytą instrukcję w danych. Potem napisz jego serce — pętlę agenta — i walidację argumentów narzędzi.
